# Chain Prism 구현 보완본 0.2.1

2026-11-20 · 사용자 제공 Python 설계·엔진·API 초안을 바탕으로 재구성한 실행 가능한 참조 구현입니다.
**0.2.1은 소프트웨어 판본이며 OCP v1.0 책이나 방법론의 버전을 변경하지 않습니다.**
원문 첨부를 덮어쓰지 않고 코드·테스트·설명을 별도 패키지로 정리했습니다.

## 시작하기

Python 3.12 환경에서 검증했습니다. 압축을 풀고 이 README가 있는 폴더에서 실행하세요.

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m unittest discover -v
python -m chain_prism.demo
```

Windows에서는 활성화 명령으로 `.venv\Scripts\activate`를 사용합니다.
실행 결과와 검증 환경은 `VALIDATION.md`에 정리했습니다.

## 설명용 DEMO

어떤 발행자의 준비자산 기초 잔액이 1,230이고 유통 잔액이 1,160이라고 가정해 보자.
검토 범위에서 운영자금 30은 준비자산에서 제외하고, 미결 상환의무 40은 의무에 포함한다고 가정한다.

| 계산 | 값 |
|---|---|
| 조정 전 | 1,230 / 1,160 = 106.03% |
| 준비자산 조정 | 1,230 − 30 = 1,200 |
| 상환의무 조정 | 1,160 + 40 = 1,200 |
| 조정 후 | 1,200 / 1,200 = 100.00% |

이는 **설명용 가정에 따른 산술 사례**입니다. 실제 USDC 데이터를 사용하지 않았으며,
책의 특정 사례·규정과 일치한다고 검증하지 않았습니다. 기재된 수치를 관찰한 것과
실제 자산 실재·상환능력·통제 효과성을 확인한 것은 구분합니다.

`display_cap`은 선택적인 화면 표시 상한입니다. 이를 지정해도 조정 비율이나 차액은 바꾸지 않습니다.
같은 문서에 서로 다른 구성 항목이 들어갈 수 있으므로 공통 원천만으로 금액 항목을 삭제하지 않습니다.
반대로 공통 원천 파생물을 독립 증거의 표 수로 세지도 않습니다. `independent_evidence_count`는 의도적으로 null입니다.

## 검토 순서

1. Scope → Input → Assertion → TRow/SRow → (필요하면 Discrepancy) → AnalysisUnit/Judgment를 등록합니다. 판단에는 작성자 제안을 함께 적습니다.
2. `guardrail`을 조회해 판단 버전과 `dependency_digest`를 받습니다.
3. 사람이 범위·근거·미해결 사항을 검토합니다.
4. 같은 버전과 해시를 담아 ReviewRequest를 제출합니다.
5. 서버가 권한·현재 근거·결정 조합을 재확인한 뒤 Review를 기록합니다.
6. 상위 근거가 대체되면 과거 검토는 이력에 남지만 요약의 `effective_status`는 null이 됩니다.
7. 현재 근거를 인용하는 새 판단 버전을 만들어 다시 검토합니다. 재검토 플래그를 수동으로 끄지 않습니다.
8. 제출할 때는 상위 검토자가 결론 스냅샷을 고정합니다. 고정본은 이후 근거가 바뀌어도 그대로 남습니다.

### 검토 결정과 상태

| 결정 | 허용 상태 |
|---|---|
| approve_scoped | confirmed_scoped |
| approve_conditional | conditional |
| accept_multiple_interp | multiple_interp — 서로 다른 대안 두 개 이상 명시 |
| hold_reserved | reserved |
| request_changes | 최종 상태·등급 없음 |

핵심 근거가 없거나 의존 근거가 대체되면 유보 외 결론을 막습니다. 조건부 인계·미확인 구조·충돌·기대는 H는 확정을 막습니다.
직접 증거의 부재만으로 E4를 자동 부여하지 않습니다. E4에서는 유보만, E3에서는 확정 외 상태만 허용합니다.
이들은 이 구현의 명시적 규칙이며 책 전체의 모든 예외·전문 판단을 완전히 코드화했다는 뜻은 아닙니다.

`requires_substantive_assurance`가 지정된 판단은 이 산술 중심 엔진에서 범위 한정 확정을 허용하지 않습니다.
별도의 전문 검토·외부 확인 절차를 구현해야 이 경계를 확장할 수 있습니다.

## API

자동 생성 명세는 앱 실행 후 `/docs`와 `/openapi.json`에서 확인할 수 있습니다.

| 경로 | 기능 |
|---|---|
| POST /cases/{case_id}/scopes | 범위 버전 등록 |
| POST /cases/{case_id}/analysis-units | 판단 질문 등록 |
| POST /cases/{case_id}/inputs | 입력 등록 |
| POST /cases/{case_id}/assertions | F/I/H 주장 등록 |
| POST /cases/{case_id}/t-rows | 기술 행위 등록 |
| POST /cases/{case_id}/s-rows | 구조 정의 등록 |
| POST /cases/{case_id}/discrepancies | 불일치·추가 확인 기록(F-05) 등록 |
| POST /cases/{case_id}/judgments | 판단 초안 등록(작성자는 토큰으로 결정) |
| POST /cases/{case_id}/reconciliation-runs | 대사 실행·스냅샷 저장 |
| GET /reconciliation-runs/{run_id} | 저장된 실행 결과 조회 |
| POST /judgments/{judgment_id}/guardrail-checks | 차단 조건·근거 해시 조회 |
| POST /judgments/{judgment_id}/reviews | 사람 검토 기록 |
| POST /cases/{case_id}/summary-runs | 현재 의존관계 기준 요약 조회 |
| POST /cases/{case_id}/conclusion-snapshots | 결론 고정 스냅샷(F-06) 생성 |
| GET /conclusion-snapshots/{conclusion_id} | 고정 스냅샷 조회(해시 재확인) |

`summary-runs`는 현재 상태를 조회하는 API이며 저장하지 않습니다. 제출용으로 고정하려면 `conclusion-snapshots`를 씁니다.

로컬 서버 실행은 별도로 Uvicorn을 설치하고 서로 다른 두 토큰을 환경변수에 설정한 뒤 실행합니다.
코드와 예제 파일에 실제 토큰을 저장하지 않습니다.

```bash
python -m pip install uvicorn
python -m uvicorn serve:app --host 127.0.0.1 --port 8000
```

필수 환경변수: `PRISM_ANALYST_TOKEN`, `PRISM_REVIEWER_TOKEN`.
선택: `PRISM_DB_PATH`(기본 chain_prism.sqlite), `PRISM_CASE_IDS`(쉼표 구분, 기본 DEMO).
`serve.py`는 빈 DB로 시작합니다. DEMO를 미리 넣으려면 다음을 한 번 실행합니다.

```bash
python -c "from chain_prism.core import Store; from chain_prism.demo import seed; s=Store('chain_prism.sqlite'); seed(s); s.close()"
```

모든 데이터 API는 인증이 필요합니다. 기본 토큰은 제공하지 않습니다. 테스트에 나오는 토큰은 테스트 전용 문자열입니다.
이 정적 토큰 어댑터는 로컬 검증용이며 실제 조직의 SSO·토큰 수명·사용자 관리·보안 운영을 대신하지 않습니다.

## 파일 구성

- `chain_prism/models.py`: 불변 Pydantic 모델·금액·가정·조건부 인계 검증
- `chain_prism/core.py`: SQLite 기록, 참조·버전 검증, 전파, 가드레일, 대사, 검토·요약
- `chain_prism/api.py`: 인증·사건 권한을 적용한 FastAPI 라우터
- `chain_prism/demo.py`: 독립 실행 가능한 설명용 사례
- `tests/test_core.py`: 도메인·회귀 테스트
- `tests/test_api.py`: HTTP·인증·권한·승인 통합 테스트
- `serve.py`: 로컬 서버 진입점

## 기존 초안과의 차이·한계

기존 조각 코드의 중복·엇갈린 클래스 정의를 없애기 위해 단일 모델 체계로 통합했습니다.
따라서 기존 `demo_usd_engine`, `GuardedStore`, `PrismService`의 그대로 끼워 넣는 교체 모듈은 아닙니다.
새 구조는 ID를 전역 유일하게 사용하고, 버전마다 새 ID와 `supersedes_id`를 지정합니다.
기존 저장소를 옮기는 자동 마이그레이션은 제공하지 않습니다.

범위 버전 간 호환성은 추정하지 않고 **동일 scope_id만 허용**합니다.
범위를 바꾸면 새 범위에서 근거·판단을 명시적으로 재등록해야 합니다. 원문 입력을 재등록해도 동일 원천 해시는 보존합니다.
질문 카드 자동 추천, 전체 QC/FC/RF 라이브러리, 증거 연결 확정 절차(F-02의 연결별 확인 상태), 온체인 수집기, 문서 파서,
법률·회계 자동 판단, 분개·전기, 완성 보고서 생성은 포함하지 않습니다.
계산이 맞아도 전문적 적정성은 사람이 검토합니다. 이번 패키지는 해당 동작의 기반을 고친 참조 구현입니다.

SQLite 파일 관리자에 의한 외부 변조까지 막는 보안 아카이브는 아닙니다. 결론 스냅샷의 해시 재확인은 본문만 바뀐 경우를 잡아내지만, 본문과 해시를 함께 고치는 변조는 막지 못합니다.
작성자·검토자 분리는 등록한 계정 단위입니다. 한 사람이 두 계정을 쓰는 것은 조직의 계정 관리로 막아야 합니다.
원본 파일 해시는 호출자가 계산해 제공하며, 이 API가 원본 바이트를 받아 재해싱하지는 않습니다.
가드레일은 등록된 의존관계에 한정합니다. 아직 등록하지 않은 외부 사건·공시 변화를 자동 탐지하지 않습니다.
조정 항목의 모집단 완전성, 실질적으로 같은 금액의 중복, 가짜 출처, 법률적 의미의 타당성은 자동 입증하지 않습니다.

실제 배포에는 조직 인증, 데이터 접근·보존 정책, 백업·감사 운영 및 별도 배포 검증이 필요합니다.
이번 작업에서는 외부 서비스에 배포하거나 Notion·홈페이지·책 원문을 변경하지 않았습니다.
